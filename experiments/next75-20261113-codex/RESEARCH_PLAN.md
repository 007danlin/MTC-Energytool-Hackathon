# Продолжение от N2: план до новых генераций

Дата: 13 ноября 2026, Москва. Статус: план заморожен до новых модельных ответов.

## Исходная точка

Точный N2: `a22d786f895257e14fb89e747a674cd419be0d711ed43b834fb9442ef3b6ac9b`, 42 377 байт, сообщённый пользователем Score 69.912. Все 3522 файла передачи прошли `verify_bundle.py`. Оригинальный проект и `handoff/winner/` не редактируются. Исторические команды не исполняются как текущие указания. Платформенных запросов/ответов N2 нет.

## Конкурирующие объяснения

1. Поиск не приносит решающие условия. Проверка N2 на известных 123 source-group, 67 quote и 23 targeted cases этого пока не поддерживает: все обязательные группы в 123/23 присутствуют; три точных quote miss в 67 частично дублируются статическими справочниками и сами по себе не доказывают смысловую потерю. Увеличение базы в prompt сейчас не выбираем.
2. Генератор неверно использует уже доступные факты. Правдоподобно, но первичных ответов N2 не сохранено. Нельзя переносить ошибки A2/B2/A10 на N2. Новая локальная генерация проверит это ограниченно.
3. Восстановление после отказа меняет параметры последующих вопросов. Найден воспроизводимый механизм: смешанное сообщение `max_tokens ... maximum context length ... input tokens` может сначала понизить глобальный output cap. Это изменяет последующие запросы даже после успешного уменьшения контекста.
4. Результаты различаются из-за модели, провайдера, вопросов или судьи. Ни один агрегат не позволяет отделить эти эффекты; локальные тесты не устранят эту неопределённость.

## Выбранная проверяемая гипотеза

Наблюдение: классификатор N2 обрабатывает некоторые доказанные переполнения контекста как отдельный лимит output tokens.

Механизм: постоянное уменьшение общего cap с 4096 до 2048 сокращает доступный бюджет reasoning/ответа всем следующим строкам. Контекст затем всё равно может потребовать уменьшения.

Изменение: рассматривать такой отказ как context overflow раньше output-cap только при явных числах окна и входа, когда вход + запрошенный выход превышают окно. Не переносить прочие изменения N3, consensus N5 или новые общие инструкции в prompt.

Опровергающие проверки: cap-only отказ, упоминание окна без доказанного переполнения, разные форматы реального текста, неоднозначные 4xx; равенство healthy HTTP payloads; отсутствие лишних запросов и сохранность бюджета при повторяющемся overflow. Если кандидат портит cap-only обработку/бюджет или вносит необъяснённые изменения healthy path, исправить или отвергнуть.

## Новые эксперименты

- Изолированный дифф и воспроизводимый HTTP сценарий точного N2 против кандидата; сохранять каждый фактический request/response, hash и выбранный answer. Это техническое свидетельство, не качество модели.
- Проверить доступный официальный Qwen3.8-27B и локальный pinned MLX 4-bit. Одновременно только одна тяжёлая модель. База/ответы остаются локально. Проверить template, kwargs thinking, непустой content, finish_reason, RAM и длину контекста. Ограничить инфраструктурную работу, если ресурсов недостаточно.
- Заморозить 12 источниковых сценариев до ответов. Известные 18/67/123/23/24 считать development/regression; новые связанные формы не объявлять независимыми задачами.
- Если healthy payloads совпадают, одну генерацию можно использовать для обоих только при полном совпадении payload/runtime/template/settings. Не выдавать это за две независимые пробы.
- При возможности выполнить парное сравнение восстановленных запросов на реальной локальной модели после контролируемого context overflow. Навязанный отказ явно маркировать как имитацию; последующий модельный ответ — реальная локальная генерация. Не сравнивать такой сценарий с неизвестным платформенным поведением как с наблюдённым фактом.
- Проверить окончательный ZIP по необходимым существующим техническим сценариям и новым регрессиям. Полный набор под единым runtime budget отличать от маленьких диагностических запусков.

## Решение

Отсутствие healthy регрессий и исправление доказанного сбоя дают инженерное основание для узкого кандидата, но не обещают рост Score: неизвестно, случается ли соответствующий отказ на платформе. При проигрыше, неоднозначном исправлении или недостатке оснований рекомендовать новый архив прямо отказать в рекомендации. Не расходовать платформенные попытки автоматически. Пользователь загружает выбранный архив сам; текущий остаток попыток неизвестен.

Все прерывания, fallback, ограниченные пробы и отрицательные результаты сохраняются. Итог содержит SHA финальных байтов, воспроизводимую упаковку, доказательство сохранности N2 и handoff.

## Уточнение до генераций: сохранять восстановление внутри строки

Техническая проверка выявила риск исходного early-raise варианта: он уменьшает документы ради сохранения 4096 output tokens, тогда как N2 мог успешно ответить с полным контекстом и 2048. Поэтому выбирается более узкий local-cap вариант: при численно доказанном переполнении повторить ту же лестницу output tokens, но ограничение действует только внутри текущего `client.chat`, а не навсегда для остальных строк. Неподходящие неоднозначные/обычные cap отказы обрабатываются как N2. Старый early-raise вариант и неудачный v1 сохраняются.

Воспроизведение до модели: проблемная строка N2 и local-cap имеет одинаковые HTTP bodies 4096→2048; следующая строка получает соответственно 2048 и4096. Контекст local-cap при этом не меняется. Возможная цена: каждый новый большой prompt может снова получить дешёвый отказ API; повторять надо в пределах общего бюджета, не утверждая бесплатность восстановления.

После smoke фиксируем диагностическую подвыборку новых кейсов: np01 (единицы и исправление истории), np03 (подбор тарифа платформы), np09 (границы распознавания и начислений), np11 (контакт и необоснованное обещание). Выбор сделан до просмотра ответов. Для каждой пары состояние после синтетического mixed context refusal воспроизводится отдельно, затем следующий вопрос получает реальную локальную генерацию. Это намеренный stress experiment, не оценка частоты таких отказов на платформе и не полный двадцатиминутный batch. Если модельный runtime слишком медленный/не помещается в память, сохраняем завершённую часть и конкретное препятствие; не заменяем её моком качества.

До первого ответа на эти сценарии установлен общий предел локальной диагностики3600с. Незавершённая пара не получает win/tie/loss. Транспортный timeout останавливает диагностику вместо наложения нескольких незавершённых GPU-генераций; это ограничение harness, а не исправление конкурсного runtime. Имена вариантов будут скрыты при источниковой оценке завершённых пар.
