# Независимый аудит runtime N2 и изолированный эксперимент

13 ноября 2026. Проверен точный `handoff/winner/source`, без изменения winner. Модели и платформа в этом аудите не вызывались. Старые команды и обещания N3/N5 рассматривались как история, а не текущие инструкции.

## Главный подтверждённый механизм

В `llm_client.py:238–250` N2 смешанный отказ, содержащий одновременно окно контекста и `max_tokens`/`completion tokens`, может классифицироваться как постоянный лимит вывода. `_lower_cap(4096)` запоминает 2048 для всех последующих строк. Это неверное обобщение: заполненное окно конкретного prompt не доказывает глобальный лимит completion сервиса.

Детерминированный HTTP-контрпример: `max_tokens is too large: maximum context length is 32768 tokens and your request has 30000 input tokens`. При 4096 output сумма не помещается, при 2048 помещается. N2 отправляет лимиты `[4096, 2048, 2048]` для двух строк, хотя вторая строка могла принять4096. Это наблюдение имитатора, а не восстановленный ответ платформы.

N3 уже менял эту область, но вместе с retry-бюджетами, паузами, probing, pace и inline-thinking. Поэтому брать N3 целиком из этого вывода нельзя. Отрицательный N3 score также не опровергает изолированный дефект.

## Проверенные альтернативы

1. **Early raise / уменьшить контекст ради4096.** Копия `runtime-probe/candidate`. При доказанном overflow передаёт отказ Consultant. В полном двухстрочном примере prompt менялся с72483 на65241 символ, а следующая строка с74327 на65022. Оба completion4096, но часть документов потеряна. Это содержательный tradeoff, не очевидное улучшение. Первый v1 также ошибочно продолжал снижать глобальный cap при reasoning=low; неудачный код и результаты сохранены в `runtime-probe/rejected-v1`.
2. **Локально снизить output, сохранить контекст.** Копия `runtime-probe/candidate-local`; предлагаемый более консервативный вариант. Сохраняет лестницу N2 внутри текущего `chat`, но контекстный отказ с явно указанными window/input не записывает в глобальный output-cap. Проблемная строка получает те же payloads4096→2048, следующая снова может запросить4096. В примере размеры всех трёх prompts точно совпали с N2:72483,72483,74327. Поведение без ошибок не меняется.

`candidate-local` изменяет только `llm_client.py`. Diff: `runtime-probe/candidate-local.patch`. Повторы, паузы, reasoning hints, prompts, retrieval, pace, workers, fallback и обычные output-cap ответы не изменены.

Ветка включается только при явно указанном числе input tokens и проверке `input + requested_output > window`. Старый `_window` умеет оценивать input из произвольного большего числа; для новой классификации это запрещено аргументом `explicit_only=True`. Неоднозначное `max_tokens too large for context` без token counts сохраняет поведение N2. Это осознанное ограничение охвата, а не доказательство исправления всех ошибок API.

Это 17 сценариев, включая default/low/retry8192, настоящий output-cap, output-cap с упоминанием окна при помещающейся сумме, неоднозначные сообщения с/без посторонних чисел, context-only, HTTP400/404/413/422, healthy и полный Consultant.

`runtime-probe/compare.py` подтверждает:

## Риски и инженерное решение

Local-cap лучше сохраняет поведение N2, чем early-raise: исправляет перенос ограничения между строками, сохраняя документы и внутристрочную лестницу. Но если практически все prompts превышают одно и то же окно, он вновь оплачивает отказ на каждой строке. В таком сценарии выигрыша в конечном output-budget нет, HTTP-нагрузка выше. При дорогих отказах, очереди или rate limit это может ухудшить общий результат. Эту цену нельзя скрывать за техническим PASS.

Если реальный API никогда не даёт распознанный смешанный отказ, patch ничего не меняет. Если даёт его редко, более короткие будущие строки могут сохранить4096/8192 вместо ошибочно закреплённых2048. Даже тогда больше output tokens не доказывает лучшие факты, и score75+ не обоснован. Для решения о конкурсном архиве нужны общий контекст результатов root и честная оценка неизвестного; этот аудит сам по себе не рекомендует тратить последнюю попытку.

## Другие найденные ограничения N2

- `consultant.py:321`: `first=False` устанавливается только после непригодного HTTP200. `status=ok` возможен после retry и перепланирования. Известно в handoff; диагностическую интерпретацию нужно исправить, не приписывать ему причинный прирост.
- `llm_client.py:313–315`: обнаружение одиночного `</think>` регистронезависимо, а `rpartition` регистрозависим. `internal analysis </THINK> Final answer.` сохраняется целиком, тогда как lowercase очищается. Воспроизведено в `runtime-probes.json`. Нет свидетельств такого ответа провайдера; правка не включена, чтобы не расширять кандидат без причины.
- `RunState.step_down`: два подряд transport/timeouts переводят docs в wide без возврата. Это существующая адаптация, не доказанный баг платформенного результата. N3 менял её и ухудшился в единственном наблюдении; переносить probing без измерения нельзя.
- Обычные русские/английские labels, JSON user/assistant и многострочные реплики в отдельных probes разобрались корректно. Убедительного нового parser-дефекта healthy path не найдено.
- Fallback-excerpt и непустой CSV не доказывают ответа по существу; аудитор не считает их качественным успехом.
