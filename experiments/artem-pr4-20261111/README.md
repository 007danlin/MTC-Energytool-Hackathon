# МТС Energytool

**Текущий статус:** A2 получил **55.969** и статус «Лучшее решение» по таблице пользователя 10 ноября, 19:24 МСК. Это на **5.531 пункта** выше v3 (50.438). Предоставленный a2.zip побайтно совпал с замороженным кандидатом A2; его код теперь является рабочей версией. V3 сохранён. [Результат A2](docs/platform-a2-result.md), [предшествующее локальное сравнение](docs/strategy-comparison-20261110.md). Локальные оценки не предсказали этот платформенный прирост.

Делаем ИИ-консультанта для сайта Energytool на Hack&Change 2026.
Бот отвечает по базе знаний, помогает выбрать решение и собирает заявку для менеджера.

Блок Даниэля реализован как общий Python-модуль для автоматического сабмита и будущего бэкенда. По сообщению пользователя балл в личном кабинете вырос с 5.836 у v2 до 50.438 у v3. V3 устраняет воспроизведённые потери ответов и улучшает поиск; вклад каждого изменения в платформенный балл отдельно не измерен. Локальные проверки доступны на Qwen3-VL-30B-A3B, а локального доступа к API платформенной Qwen3.8-27B и интеграции с соседними модулями нет. Mock-проверки отделены от качества консультации.

## Что готово

- OpenAI-совместимый клиент: настройки из окружения, тайм-ауты, ограниченные повторы 429/5xx/сетевых ошибок, отдельные коды ошибок, отсутствие секретов в диагностике.
- CSV-консультант с историей и прямым текстовым ответом; отдельный режим бэкенда с проверяемыми цитатами и структурированной заявкой.
- Проверка происхождения контактов из реплик клиента, исправления и отзыв полей; заявка не считается отправленной.
- Изоляция сессий, JSON-адаптер для бэкенда и контракт заменяемого поиска.
- `solution.py`, атомарный UTF-8 CSV, сборщик минимального ZIP и проверка запуска распакованного ZIP через локальный HTTP API.
- 30 сценариев, автоматические тесты, локальные отчёты и Docker-конфигурация запуска ML-сабмита.

## Архитектура

```text
CSV или текущая сессия бэкенда
  → разбор истории / проверка session_id
  → Retriever.search(запрос с контекстом)
  → релевантные разделы + ограничения из базы
  → один вызов /chat/completions
  → CSV: готовый ответ клиенту → submission.csv
  → бэкенд: проверка JSON, цитат и контактов → ответ + источники + заявка + время
```

В CSV отсутствует проверка служебной JSON-схемы: полезный ответ больше не отбрасывается из-за неточной цитаты или отсутствия полей заявки. Источники остаются в промпте; статус `answered` в этом режиме означает успешное получение текста, а не доказанную фактологическую правильность. В бэкенде при ошибке структуры/цитат допускается одна попытка исправления. Транспортные повторы ограничены отдельно. Вся история принадлежит вызывающему бэкенду; сервис не хранит её между вызовами. Для генерации используется модель из окружения организаторов.

Пока поиска Артёма нет, работает резервный BM25 с отдельным весом заголовков, текущего вопроса и истории. Справочные ограничения выбираются по теме, вместо добавления всех справочников к любому вопросу. Индекс создаётся в памяти при запуске. Данные, индекс и демонстрационные ответы в ZIP не входят. Ответы из демонстрационного CSV не используются генератором.

## Быстрая проверка без API

Нужен Python 3.9+. Сторонние Python-пакеты не требуются. Организаторские данные поместите локально:

```text
data/
  questions.csv         # локально — demo_questions.csv, переименованный
  knowledge-base.zip
```

```bash
python3 tools/check_all.py
```

Команда запускает тесты, 30 сценариев на mock, проверку наличия аннотированных сведений в контексте, сборку ZIP и его запуск в чистой папке через локальный тестовый HTTP API. Порты сервера выбираются автоматически на 127.0.0.1. Внешняя модель не вызывается.

Результаты:

- `artifacts/daniel-submission.zip` — автоматический сабмит;
- `artifacts/daniel-submission.manifest.json` — состав и SHA-256;
- `reports/validation.json` — сводка воспроизводимых проверок;
- `reports/private/offline-results.json` и `.md` — фактические mock-ответы, критерии, источники, время по 30 сценариям.

Все 30 результатов mock относятся к инфраструктуре. Наличие ожидаемого фрагмента в контексте не доказывает качество ответа модели или высокий балл судьи.

## Запуск с моделью

Скопируйте `.env.example` в `.env` и заполните доступный OpenAI-совместимый endpoint, ключ и модель. `.env` не загружается Python автоматически: экспортируйте переменные средствами среды запуска. Для zsh/bash:

```bash
set -a
source .env
set +a
python3 solution.py
```

Результат — `submission.csv` в текущем рабочем каталоге. Отсутствие настроек даёт код выхода 2 с именами недостающих переменных. Если отдельный вызов модели не удался, строка CSV содержит явное сообщение о техническом сбое, а агрегированная статистика ошибок выводится в stdout. Непустая строка ошибки не считается качественным ответом.

В stderr выводятся безопасные события этапов запуска, контрольных сохранений и HTTP-коды ошибок. Ключи, URL API, вопросы и ответы в этих событиях не записываются. Начальный CSV со всеми ID создаётся перед первым сетевым запросом и заменяется по мере получения ответов. Поиск входных файлов поддерживает также имена `train.csv`, `knowledge_base.zip`, `kb.zip` из примера организаторов; вопросы и база должны находиться в одной папке. Колонки входного CSV определяются по именам, порядок и дополнительные именованные колонки не мешают запуску. Выход всегда содержит только `id,answer`.

```bash
python3 tools/evaluate.py --mode live
```

Эта команда выполняет 18 демонстрационных сценариев через фактический CSV-режим и 12 сценариев контракта бэкенда. Она сохраняет полный локальный отчёт и требует содержательной проверки по рубрикам, не отправляет сабмит и не вычисляет закрытый Score. В сценарии 30 ошибки API намеренно моделируются даже в live-режиме.

## Переменные

| Переменная | По умолчанию / назначение |
|---|---|
| LLM_BASE_URL, OPENAI_BASE_URL, BASE_URL | Обязательный адрес; первый непустой имеет приоритет; BASE_URL добавлен для совместимости с примером организаторов |
| LLM_API_KEY, OPENAI_API_KEY | Обязательный ключ; не выводится в repr/логах |
| LLM_MODEL, OPENAI_MODEL, GEN_MODEL | Обязательный идентификатор модели; первый непустой |
| DATA_DIR | data |
| TEMPERATURE | 0.0; ограничивается диапазоном 0–2 |
| MAX_TOKENS | 2048; положительное целое значение платформы передаётся без прежнего ограничения 128–16384 |
| MAX_WORKERS | 3; значение ограничивается диапазоном 1–8 без остановки решения |
| LLM_TIMEOUT | 90 секунд на попытку, как в примере организатора |
| LLM_ATTEMPTS | 3, допустимо 1–4 |
| TOP_K | 12 ранжированных фрагментов плюс относящиеся к теме ограничения; ограничивается диапазоном 1–40 |
| CONTEXT_CHARS | 32 000 символов базы; фрагменты не обрезаются |
| RUN_BUDGET_SECONDS | 1120 секунд общего бюджета, максимум 1140 |

Тайм-аут HTTP ограничивает отдельный запрос; общий бюджет проверяется перед запросами и повторами. Это не замена жёсткому ограничению контейнера, особенно при зависании системного DNS. Значение MAX_WORKERS подбирается после измерения реального прокси. CHUNKER, EMB_MODEL и RERANKER_* для резервного лексического поиска не используются.

Некорректные необязательные настройки TEMPERATURE, MAX_TOKENS, MAX_WORKERS и TOP_K заменяются безопасными значениями по умолчанию с диагностикой, как в примере организаторов. Отсутствие URL, ключа или идентификатора модели остаётся ошибкой настройки. Обрыв генерации по лимиту токенов фиксируется как `truncated_response` без повторения идентичного запроса; низкий MAX_TOKENS может быть недостаточен для структурированного ответа.

## Docker

После подготовки `data/` и `.env`:

```bash
docker compose up --build --abort-on-container-exit --exit-code-from ml-submit
docker compose cp ml-submit:/app/submission.csv ./submission.csv
```

Это контейнер ML-сабмита, без веб-сервера и открытых портов. Входные данные подключены только для чтения, процесс работает без root. Для обращения к API на хосте из Docker используйте доступное контейнеру имя, например `host.docker.internal`, если его поддерживает ваша среда. Итоговый compose с бэкендом и интерфейсом должен быть объединён командой; этот контейнер сам по себе не закрывает требование веб-прототипа.

Проверка Docker без ключей и реальной модели:

```bash
python3 tools/check_all.py --docker
```

Она собирает образ, запускает Python-тесты внутри него и проверяет Compose-сервис с тестовым API в отдельной внутренней сети. Проверяются все 18 строк CSV, восстановление после 429, запуск без root, доступ к данным только для чтения, ошибка при отсутствии настроек и совпадение файлов образа с итоговым ZIP. Тестовые контейнеры и сеть удаляются автоматически; `.env` не используется и не изменяется.

Фактическая версия Python, число тестов, результат обработки 18 вопросов и контрольная сумма ZIP находятся в `reports/docker-validation.json`; общий отчёт с `--docker` также содержит раздел `docker`. Реальная модель в этой проверке не вызывается.

Для проверки упакованного решения также на Python 3.9:

```bash
python3 tools/check_all.py --docker --python-compat python:3.9-slim
```

После сообщения платформы об ошибке скоринга выполнен отдельный разбор совместимости: [docs/api-compatibility-audit.md](docs/api-compatibility-audit.md). Проверка Python 3.9 сохраняется в `reports/python-compatibility.json`.

После результата v2 подготовлен [разбор низкого Score и изменений v3](docs/score-improvement-v3.md). Текущая подтверждённая версия — `artifacts/daniel-submission-a2.zip`; v3 и v2 сохранены для сравнения.

Ограничения текущей версии: локальные ответы проверены на Qwen3-VL-30B-A3B, которая отличается от платформенной Qwen3.8-27B; семантическая связь каждого утверждения с источником не доказывается программно; классификация намерений и полнота резюме зависят от модели; контакт проверяется по формату и происхождению, а не по существованию; поиск пока резервный, без эмбеддингов; реального бэкенда, истории в БД, интерфейса и CRM в этом блоке нет. Для отправки автоматического сабмита выбирайте ZIP из `artifacts/`, а не архив всей папки проекта.
