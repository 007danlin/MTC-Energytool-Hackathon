# Аудит совместимости сабмита с платформой

Обновление после этого аудита: пользователь сообщил о завершённой оценке v2 — 5.836 в личном кабинете / 0.0584 в лидерборде. Подготовлена новая версия; актуальный разбор — [score-improvement-v3.md](score-improvement-v3.md). Ниже сохранены результаты первоначальной диагностики ошибки v1.

10 ноября 2026 года после сообщения «Ошибка скоринга сабмита. Попробуйте позже» повторно проверены технический регламент DOCX, пример `sample_submission.zip`, текущий код и первоначальный ZIP. У пользователя нет логов исполнения или сформированного CSV. Сообщение платформы не позволяет установить, упал ли Python, вызов генерации, загрузка результата или LLM-судья.

**В коде обнаружены и исправлены воспроизводимые ошибки совместимости. Какая из них проявилась на платформе, неизвестно.** До аудита тесты проверяли Python 3.11 и основной набор переменных; этого было недостаточно, чтобы исключить другие варианты среды запуска.

## Подтверждённые проблемы

| Условие | Прежнее поведение | Исправление |
|---|---|---|
| Python 3.9 | Импорт solution.py завершается TypeError на аннотации `LeadState \| None`; до API и CSV выполнение не доходит | Отложенные аннотации; весь набор тестов выполнен на коде ZIP в Python 3.9 |
| Адрес задан только через BASE_URL | Ошибка отсутствующей настройки, выход 2 до создания CSV | Добавлен fallback BASE_URL, предусмотренный примером организаторов; официальные LLM_BASE_URL/OPENAI_BASE_URL сохраняют приоритет |
| MAX_TOKENS=64 или 32768 | Необоснованный отказ из-за собственного диапазона 128–16384 | Любое положительное целое значение платформы передаётся модели; произвольной границы из старой версии нет |
| MAX_WORKERS=16 или TOP_K=50 | Решение завершалось целиком из-за превышения локальных границ | Число потоков и фрагментов ограничивается ресурсными границами, как в примере организаторов |
| Колонки CSV идут question,id | Вход отвергался, хотя обязательные именованные колонки присутствуют | Чтение по именам колонок, строгая проверка ID и сохранение выходного формата id,answer |

В регламенте не указана версия Python и не заданы прежние числовые границы нашего валидатора. BASE_URL присутствует в примере организаторов, хотя текст регламента перечисляет LLM_BASE_URL и OPENAI_BASE_URL. Это обосновывает поддержку дополнительных вариантов, но не доказывает фактические настройки платформы.

Отчёт воспроизведения старых ошибок: `reports/api-audit-before.json`. Исходный отправленный вариант сохранён локально как `artifacts/daniel-submission-before-api-audit.zip`; он не предназначен для новой загрузки.

## Что проверено в HTTP

Endpoint и заголовок уже соответствовали регламенту: `{base_url}/chat/completions`, `Authorization: Bearer ...`. Модель берётся из LLM_MODEL/OPENAI_MODEL/GEN_MODEL, запроса к стороннему фиксированному сервису нет. Отсутствующий ключ не заменяется выдуманным рабочим ключом.

Новые проверки запускают настоящий локальный HTTP-сервер и проверяют переданные URL, ключ-заглушку, идентификатор модели, температуру, MAX_TOKENS и русский текст. Проверены все три имени адреса API и соединения с заголовком `Connection: close`.

Исправлен учёт оставшегося времени при чтении тела закрывающегося HTTP-соединения: после получения заголовков HTTPConnection мог обнулить ссылку conn.sock, и оставшийся бюджет не применялся к чтению тела. Теперь ссылка на сокет сохраняется до завершения чтения, а ответ и соединение закрываются явно. Общий лимит платформы всё равно остаётся необходимым: системный DNS не получает жёсткого ограничения времени от этого кода.

Ответ с finish_reason=length больше не вызывает несколько одинаковых повторов с тем же лимитом токенов. Он получает код truncated_response. Это экономит время при недостаточном бюджете генерации, но не превращает обрезанный ответ в корректную консультацию. Транспортные повторы 429, 5xx и сетевых сбоев сохранены.

HTTP-статус больше не теряется между клиентом и результатом консультанта. В stderr выводятся только этапы запуска, порядковые номера строк, безопасные коды ошибок и числовой HTTP-статус. Ключи, адрес API, вопросы, ответы и тела HTTP-ошибок не логируются.

## Запуск и сохранение результата

Поддержаны запасные имена входных файлов из примера: train.csv, knowledge_base.zip и kb.zip. Вопросы и база выбираются парой из одной папки, чтобы не смешать источники. Проверяется также расположение относительного DATA_DIR рядом с solution.py. Стандартные questions.csv и knowledge-base.zip имеют приоритет.

CSV со всеми ID создаётся перед первым запросом модели, затем атомарно обновляется. До получения ответа строка явно содержит сообщение о технической недоступности; такие строки не считаются успешной генерацией. Это защищает наличие результата при частичном выполнении, но не гарантирует положительный балл.

Сторонние зависимости не требуются. requirements.txt остаётся в корне ZIP; пустой список пакетов не запрещён предоставленным регламентом. Никаких данных, индексов, конфигураций или тестовых серверов в автоматическом ZIP нет.

## Результат проверки исправленной версии

- 47 программных тестов прошли локально и внутри основного образа Python 3.11.18.
- Все 47 тестов прошли на коде из ZIP в отдельном контейнере Python 3.9.25.
- 30 сценариев протокола прошли с заглушкой; наличие аннотированных сведений подтверждено для 18 демонстрационных вопросов.
- Распакованный ZIP обработал 18 вопросов через локальный HTTP API.
- Compose-контейнер обработал 18 вопросов, выполнил 19 запросов с одним восстановлением после 429 и завершился с кодом 0.
- Подтверждены UID 10001, входные данные только для чтения и побайтовое совпадение кода образа с ZIP.

Команда воспроизведения:

```bash
python3 tools/check_all.py --docker --python-compat python:3.9-slim
```

Точные контрольные суммы и версии: `reports/validation.json`, `reports/docker-validation.json`, `reports/python-compatibility.json`, `artifacts/daniel-submission-v2.manifest.json`.

Для повторной отправки подготовлен **daniel-submission-v2.zip**. Подтверждение устранения именно платформенной ошибки возможно только после новой обработки. Доступ к реальной Qwen отсутствует, поэтому качество её ответов, соблюдение ею JSON-формата и итоговый Score всё ещё не проверены. Сбой LLM-судьи остаётся отдельной возможностью, которую локальные тесты не могут ни подтвердить, ни исключить.
