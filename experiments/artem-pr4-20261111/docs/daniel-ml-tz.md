# ТЗ: ML/LLM-часть — Даниэль

Проект: МТС Energytool, Hack&Change 2026.
Дата: 9 ноября 2026 года.
Исходное состояние: реализация ещё не начата.

## Цель

Сделать модуль консультанта, который отвечает по базе знаний Energytool, учитывает историю, уточняет задачу клиента и формирует заявку менеджеру. Один и тот же модуль используется в автоматическом сабмите и веб-прототипе.

Твоя зона ответственности — логика LLM-консультанта и подготовка автоматического сабмита. Поиск делает Артём, хранение и API — Игорь, интерфейс — Георгий.

Требования организаторов ниже отделены от предложенного командного объёма: распределение задач, интерфейсы и набор из 30 проверок — рабочая договорённость команды, а не дополнительные условия МТС.

## Важные уточнения

- На платформе адрес API, ключ и модель подставляются автоматически. Возможность обращаться к этому API с локального компьютера регламент не обещает. Для локальных проверок нужен доступный способ вызова модели; без него можно проверить обработку данных на заглушке, но не качество генерации.
- PDF допускает готовый индекс в решении, но технический регламент запрещает включать индексы и данные в автоматический сабмит. Для упаковки ориентируемся на технический регламент. Расхождение нужно уточнить у организаторов; до уточнения поиск готовится при запуске из переданной платформой базы.
- Автоматический ZIP-сабмит и финальная сдача проекта — разные артефакты. Ограничения на содержимое автоматического ZIP не означают, что финальному репозиторию не нужны README, Docker и остальные материалы.

## 2. Согласовать интерфейсы с командой

Предлагаемый минимальный договор:

| Направление | Что передаётся |
| --- | --- |
| Твой модуль → поиск Артёма | Поисковый запрос с необходимым контекстом текущего диалога |
| Артём → твой модуль | Найденные фрагменты: текст, идентификатор документа и идентификатор фрагмента |
| Игорь → твой модуль | Сообщения текущего диалога и уже собранные поля заявки |
| Твой модуль → Игорь | Ответ, использованные источники, время обработки, обновлённые поля заявки и признак её готовности |

Названия и типы полей согласовать до интеграции. В автоматическом сабмите наружу выводится только предусмотренный регламентом CSV.

До готовности поиска работать с вручную выбранными реальными фрагментами базы.

**Критерий готовности:** есть по одному примеру входа и выхода, понятному Даниэлю, Артёму и Игорю.

## 3. Реализовать клиент модели

Сделать отдельный модуль обращения к OpenAI-совместимому API:

- Адрес брать из `LLM_BASE_URL` или `OPENAI_BASE_URL`.
- Ключ брать из `LLM_API_KEY` или `OPENAI_API_KEY`.
- Идентификатор модели брать из `LLM_MODEL`, `OPENAI_MODEL` или `GEN_MODEL`, а не фиксировать в коде.
- Использовать endpoint `/chat/completions`.
- Учитывать `TEMPERATURE` и `MAX_TOKENS`.
- Задать тайм-ауты и ограниченные повторы для временных ошибок, включая 429, 5xx и сетевые сбои.
- Обрабатывать пустой или некорректный ответ.
- Не записывать ключи в код и логи.
- Отличать техническую недоступность модели от отсутствия сведений в базе.

На автоматической проверке используется Qwen3.8-27B. Самостоятельно разворачивать её не требуется.

**Критерий готовности:** тестовый вызов возвращает ответ; ошибки и отсутствие настроек дают понятную диагностику. Проверка на заглушке отдельно помечена и не считается проверкой качества модели.

## 4. Реализовать поведение консультанта

Бот должен:

- Отвечать на последнюю реплику с учётом предыдущего разговора.
- Использовать только подтверждённые сведения из базы для фактов о продуктах, ценах, характеристиках и условиях.
- Сведения о клиенте брать из текущего диалога.
- Сначала отвечать на понятный вопрос, затем при необходимости уточнять.
- Различать нехватку данных о клиенте и отсутствие ответа в базе.
- Предлагать подходящий продукт с объяснением, почему он подходит.
- Сохранять оговорки: ориентир стоимости не превращать в точную цену, возможный эффект — в гарантию.
- При вопросах вне компетенции предлагать специалиста. Настройка конкретных приборов и техническая документация не входят в сценарий консультации.
- Обычно укладываться в 150 слов. Более длинный ответ допускается, когда вопрос этого требует; ограничение не относится к резюме для менеджера.
- Продолжать консультацию, если клиент пока не хочет оставлять телефон.
- Не переносить информацию между независимыми диалогами.

В первой версии достаточно последовательности «поиск → формирование контекста → генерация». Дополнительные агенты — только после работающей версии и проверки их пользы.

**Критерий готовности:** бот проходит сценарии проверки без выдуманных фактов и потери существенного контекста.

## 5. Реализовать формирование заявки

Собирать ФИО, телефон и компанию. Уточнять только недостающие сведения, учитывать исправления пользователя.

В резюме передавать:

- задачу клиента и сведения об объекте;
- обсуждавшиеся продукты;
- известные параметры и ограничения;
- вопросы, которые должен уточнить менеджер.

Не додумывать контакты или характеристики объекта. Не утверждать, что заявка отправлена менеджеру, если система лишь подготовила её.

Реальная интеграция с CRM, сайтом или почтой не требуется. Использовать только тестовые или выдуманные персональные данные.

**Критерий готовности:** модуль возвращает структурированные поля и резюме, Игорь может сохранить их. Неполная заявка не отмечается как готовая.

## 6. Подготовить автоматический сабмит

Даниэль отвечает за точку входа и упаковку. Артём предоставляет рабочий модуль поиска.

Требования технического регламента:

- Читать `questions.csv` и `knowledge-base.zip` из `DATA_DIR`, по умолчанию `data`.
- Входной CSV содержит `id,question`. Каждая строка — независимый тест-кейс.
- Историю внутри `question` учитывать при ответе на последнюю реплику.
- Создавать `submission.csv` в рабочем каталоге.
- Выходной CSV содержит ровно две колонки: `id,answer`.
- Для каждого входного ID нужен один непустой ответ; ID не повторяются.
- Использовать UTF-8 и корректное CSV-экранирование.
- Максимальная длина ответа — 10 000 символов.
- `solution.py`, необходимые дополнительные `.py`-модули и `requirements.txt` должны находиться в корне ZIP, без внешней папки.
- Необходимые для запуска модули нельзя оставлять во вложенных папках. Промпты не должны зависеть от отдельных файлов конфигурации, которые платформа не переносит.
- В ZIP не включать данные, индексы, конфигурации, `.whl` и ключи.
- Зависимости брать из разрешённого списка с зафиксированными версиями. Не запускать `pip install` из решения.
- Промежуточные файлы можно создавать в рабочем каталоге или `/tmp`.

Лимиты:

| Параметр | Ограничение |
| --- | --- |
| Время запуска | До 20 минут, включая подготовку поиска |
| CPU | 8 |
| RAM | 16 ГБ |
| Размер ZIP | До 128 МБ |
| Сабмиты | 5 в день на команду, сброс в 00:00 МСК |

Параллельные запросы ограничивать с учётом настроек и лимитов сервиса. Реранкер необязателен.

**Критерий готовности:** локально формируется корректный CSV, затем хотя бы один сабмит успешно проходит обработку платформой и получает оценку. Непустой CSV сам по себе не подтверждает качество ответов.

## 7. Провести 30 проверок

Предложенный внутренний объём: **18 демонстрационных примеров + 12 собственных сценариев**. Это критерий приёмки командной работы, а не дополнительное требование организаторов.

Дополнительные сценарии:

1. Неясное описание проблемы.
2. Ответа нет в базе.
3. Вопрос вне темы.
4. Запрос гарантированной цены или экономии.
5. Запрос настройки конкретного прибора.
6. Смена темы и возврат к предыдущей.
7. Новый диалог без старого контекста.
8. Попытка заставить бота игнорировать ограничения.
9. Отказ оставлять контакты.
10. Сбор заявки по частям.
11. Исправление контактов или параметров объекта.
12. Ошибка API или пустой ответ модели.

Для каждого записать ожидаемое поведение, фактический ответ, источники, время и результат проверки. Вместе с Артёмом отделять ошибки поиска от ошибок генерации.

Проверки диалогов и заявок проводить через общий модуль; проверку нового диалога дополнительно повторить после интеграции с бэкендом. Не сравнивать ответы только по буквальному совпадению с демонстрационными образцами.

**Критерий готовности:** все 30 проверок выполнены, результаты сохранены; ошибки формата, смешение сессий, выдуманные контакты и неподтверждённые обещания исправлены. Остальные недостатки перечислены явно.

## Границы ответственности

В задачи Даниэля не входят:

- разработка поиска, чанкинга и индекса с нуля — Артём;
- фронтенд — Георгий;
- база сессий, хранение истории и заявок, API приложения — Игорь;
- реальная CRM-интеграция;
- обучение собственной модели.

На стыках Даниэль участвует в проверке. История хранится бэкендом, а модуль консультанта использует только переданную историю текущей сессии. Архив старых сессий не должен автоматически попадать в контекст новой.

Исходные данные организаторов и их копии не публиковать в открытых репозиториях или общедоступных хранилищах. Рабочие ключи не включать в материалы сдачи.

## Порядок работы

1. Изучить материалы и выписать ограничения.
2. Согласовать форматы данных с Артёмом и Игорем.
3. Проверить вызов модели или подготовить клиент с заглушкой до появления доступа.
4. Получить ответы на вручную выбранных фрагментах базы.
5. Подключить поиск Артёма.
6. Подготовить и отправить ранний сабмит.
7. Доработать заявку и подключить модуль к бэкенду.
8. Выполнить итоговые проверки и передать документацию.

**Первая контрольная точка:** один вопрос из демонстрационного набора проходит через твой код и получает ответ модели по реальным фрагментам базы. Поиск, бэкенд и фронтенд для этого ждать не нужно.

Сроки этапов назначаются после уточнения дедлайна хакатона и доступного времени команды.
