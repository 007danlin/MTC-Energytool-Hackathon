# Контракт интеграции ML

Версия контракта `1.0` реализована в `contracts.py`, адаптер для JSON — `integration.py`. Это конкретное предложение для Артёма и Игоря; их подтверждение и проверка в командном бэкенде ещё не состоялись.

Начиная с v3, автоматический `solution.py` использует `respond(..., answer_only=True)` и запрашивает только текст ответа. Этот режим не извлекает новые контакты и не возвращает проверенные цитаты; `debug.retrieved_sources` означает только переданный контекст, `evidence_validation=not_performed`. Для бэкенда используйте адаптер ниже: он сохраняет полный контракт и не включает этот режим.

## Подключение

```python
from integration import create_consultant, respond_json

service = create_consultant("data/knowledge-base.zip")
result = respond_json(service, {
    "session_id": "demo-001",
    "messages": [{"role": "user", "content": "Нужен учёт по арендаторам. С чего начать?"}],
    "lead": None,
})
```

Создавайте `service` один раз при запуске приложения. Метод синхронный; в FastAPI вызывайте его через `run_in_threadpool` / `asyncio.to_thread`, с ограничением числа параллельных запросов. Не блокируйте основной event loop.

Бэкенд хранит историю и заявки. На каждый вызов передаётся **полная история только текущей сессии**, последняя реплика — `user`. Допустимы роли `user` и `assistant`; `system` от клиента не принимается. Предыдущий `result["lead"]` можно передать в следующем запросе с тем же session_id. Индексы доказательств относятся к полной истории, поэтому нельзя обрезать её начало, сохраняя старые индексы. Предел — 200 сообщений / 100 000 символов; превышение даёт понятную ошибку вместо скрытой потери контекста.

«Новый диалог» создаёт новый ID, пустые messages и lead=None. Архив старой сессии остаётся в БД, но не передаётся в ML. Между ID модуль не хранит историю. Несовпадение ID заявки и сессии отклоняется. Параллельные реплики одной сессии бэкенд должен сериализовать или защищать версией истории.

## Результат

Сокращённый пример структуры, а не результат проверки реальной модели:

```json
{
  "schema_version": "1.0",
  "answer": "Ответ клиенту",
  "status": "clarification",
  "sources": [],
  "elapsed_ms": 123,
  "lead": {
    "session_id": "demo-001",
    "fields": {},
    "evidence": {},
    "requested": false,
    "declined": false
  },
  "lead_ready": false,
  "summary": {
    "task": [], "object": [], "parameters": [], "constraints": [],
    "products": [], "manager_questions": [], "contacts": {},
    "missing_fields": ["full_name", "phone", "company"],
    "delivery_status": "draft", "sent": false
  },
  "debug": {"retrieved_sources": [], "context_chars": 0, "repairs": 0, "error_code": null}
}
```

| Поле | Значение |
|---|---|
| status | answered, clarification, knowledge_gap, out_of_scope, technical_error |
| sources | Только приведённые моделью и проверенные по тексту цитаты: document_id, chunk_id, source_id, quote |
| debug.retrieved_sources | Все переданные модели фрагменты; это не утверждение, что каждый использован |
| lead.fields | full_name, phone, company; отсутствующие значения отсутствуют в словаре |
| lead.evidence | Цитата user и message_index для поля/намерения |
| lead_ready | Все три поля валидны, имя содержит минимум два слова, есть намерение оформить заявку, нет отказа |
| summary | Задача, объект, параметры и ограничения дословно из подтверждённых реплик; продукты и вопросы менеджеру |
| summary.sent | Всегда false; внешней интеграции нет |
| error_code | Код без ключа, URL, тела ответа API и персональных данных; при HTTP-ошибке debug.http_status сохраняет номер статуса |

Проверка номера синтаксическая (10–15 цифр), она не подтверждает существование телефона. ФИО из двух слов допускается, поскольку отчество есть не у всех; модель должна уточнить полноту имени по контексту. Наличие точной цитаты подтверждает происхождение сведений, но не доказывает правильность всех логических выводов модели. Вопросы менеджеру — предложения модели, а не установленные факты.

## Подключение поиска Артёма

```python
from contracts import Fragment

class ArtemRetriever:
    def search(self, query: str, top_k: int = 12):
        # Адаптировать реальный результат поиска Артёма:
        return [Fragment(
            document_id="путь/документ.md",
            chunk_id="stable-section-id",
            text="Полный релевантный фрагмент вместе с существенными оговорками",
            score=0.95,
        )]

service = create_consultant("data/knowledge-base.zip", retriever=ArtemRetriever())
```

Запрос содержит последнюю реплику и предыдущие факты клиента. Последние вопросы ассистента учитываются ограниченным объёмом, чтобы сохранить тему ответа клиента. Фрагменты должны иметь стабильные уникальные идентификаторы, текст и необходимые оговорки; адаптер не должен возвращать чужие сессии. Передаётся до CONTEXT_CHARS символов, без обрезки отдельного фрагмента. `FixedRetriever` позволяет проверить реальные вручную выбранные фрагменты без поиска.

Текущий `LexicalRetriever` — резервный поиск по всем разделам Markdown, с нормализацией русских форм и разговорных терминов. Он не заменяет согласование с Артёмом. Семантический поиск, эмбеддинги и реранкер не подключены; добавлять их стоит после сравнения на тех же 30 сценариях по качеству и задержке.

## Приёмка с Игорем

1. Консультация → ФИО → телефон → компания → `lead_ready=true`, `sent=false`.
2. Исправить телефон и параметр объекта; проверить текущую заявку и сохранённую историю.
3. Отказаться от телефона; бот продолжает консультацию, заявка не готова.
4. Создать новый диалог, спросить о старых контактах; старые поля не возвращаются, архив остаётся доступен.
5. Проверить две параллельные разные сессии и сериализацию двух реплик одной сессии.
6. Отключить API, затем восстановить: отдельный технический статус, история не теряется.
7. В режиме отладки показать использованные источники и время, не выдавать клиенту ключи или скрытые сообщения.

Ответ модели и цитаты при отображении должны экранироваться как пользовательский текст; не вставляйте их через необработанный HTML. Авторизация доступа к архивам и заявкам относится к бэкенду.

При `technical_error` сохраняйте сообщение об ошибке в истории, но не заменяйте последнее успешное резюме заявки пустым резюме ошибки. Восстановленная из доказательств `lead` остаётся доступной, а задача и параметры будут пересобраны из полной истории при следующем успешном вызове.
