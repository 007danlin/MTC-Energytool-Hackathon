# МТС EnergyTool — ИИ-консультант для сайта

Hack&Change 2026. Клиент описывает задачу, уточняет её в диалоге и сохраняет заявку с карточкой потребности. Менеджер видит заявку в очереди; специалист отвечает на вопросы, которых нет в базе. Проверенные редактором знания подключаются к поиску. Для явно названной интеграции без найденного подтверждения совместимость не предполагается: вопрос направляется специалисту.

**Финальная сдача — самодостаточный ZIP с исходниками, документацией и PDF.** По решению владельца репозиторий остаётся приватным, доступ жюри не открывался. В кейсе, стр. 8, доступ связан со сдачей через PDF; новая форма упоминает приватный репозиторий без этого уточнения. Проверка и остающиеся условия: [аудит финальной сдачи](docs/final-submission-audit.md). Лучший сообщённый результат платформы — **69,912 у отдельного N2**; это балл платформы, не точность текущего веб-чата.

Материалы защиты: [презентация Артёма от 15 ноября и замечания](deliverables/2026-11-15/README.md), [предыдущая презентация и демо](deliverables/2026-11-14/README.md).

## Запуск через Docker

Нужен Docker Desktop / Docker Engine с Compose. Веб использует внешний OpenAI-совместимый API. Для автоматической оценки организаторы передают модель **Qwen3.8-27B** и параметры подключения; идентификатор берётся из окружения, в коде не закреплён.

1. Создайте `.env.web` из `.env.web.example`. Впишите выданные **адрес, ключ и идентификатор модели**. Пример содержит неработающие заглушки. При отсутствии выданного доступа используйте собственный совместимый API; локальная Ollama приведена отдельно в `.env.local.example`.
2. Поместите выданную организаторами базу в `data/knowledge-base.zip`. В Git её нет. В закрытом комплекте сдачи она может находиться рядом с исходниками; не публикуйте её.
3. Выполните одну команду запуска всех компонентов:

```bash
docker compose up --build -d
```

Откройте [консультацию](http://127.0.0.1:8768/consultation.html), [заявки](http://127.0.0.1:8768/applications.html) или [рабочее место специалиста](http://127.0.0.1:8768/specialist.html). Проверка готовности: `curl http://127.0.0.1:8768/health/ready`. Это проверка сервисов, а не доступности/качества модели: проверяйте её первым сообщением.

Остановить: `docker compose down`. История сохранится в именованном томе. **Не используйте `down -v`, если история нужна.** Совместимый прежний запуск: `docker compose -f compose.web.yaml up --build -d`.

## Основной сценарий проверки

1. Вопрос: «Есть счётчики на производстве, но показания переписываем вручную. Как автоматизировать учёт?» Дождитесь ответа; в меню включите отладку и проверьте документы, время, статус и режим поиска.
2. Дополните сведения. Карточка слева разделяет объект, задачу, факты и условия. Изменения редактора сначала попадают в черновик; отправленное сообщение не изменяется задним числом. Уже известные сведения не должны запрашиваться повторно.
3. Нажмите «Подготовить заявку». Достаточно **телефона или email**; имя и компания необязательны. Используйте тестовый `jury@example.test`. Проверьте карточку, сохраните и скачайте TXT. Статус означает сохранение в прототипе, а не отправку в CRM.
4. Откройте «Заявки». Найдите заявку по шестизначному номеру, откройте карточку, измените сведения и переведите её в разбор/принятые. Обновите страницу: изменения должны сохраниться. В метриках включите демоданные, поскольку демонстрационные сессии по умолчанию исключены.
5. «Новый диалог» создаёт пустой контекст. В «Истории диалогов» откройте прежнюю переписку и нажмите «Продолжить этот диалог». Выход на сайт сохраняет текущий разговор; следующий вход возвращает к нему. Черновики сообщения и заявки сохраняются в этой вкладке браузера, история и сохранённые заявки — на сервере.
6. Для неизвестной интеграции консультант должен обозначить отсутствие подтверждения. Ответ со статусом `knowledge_gap` создаёт вопрос в очереди специалиста. Техническая ошибка модели не выдаётся за отсутствие знаний.
7. Прервите ожидание ответа. История проверяется автоматически, можно писать черновик и продолжить после получения ответа. После 20 секунд ожидания и после прерывания доступна кнопка «Позвать оператора»: она открывает форму заявки, которую можно сохранить, пока модель ещё отвечает. Это заявка в очередь, а не мгновенный звонок или подключение живого чата. Аварийный перезапуск во время запроса оставляет вопрос и открывает повторную попытку.

## Специалист и проверенные знания

На `/specialist.html` введите идентификатор оператора, роль и ключ. Для локального демо ключ по умолчанию — `local-demo-operator`. Его можно заменить переменной **хоста Compose** `OPERATOR_TOKEN`; при публикации наружу нужен полноценный вход, а не этот демонстрационный механизм.

- Координатор назначает вопрос идентификатору специалиста.
- Специалист под своим идентификатором пишет ответ. Он появляется в сохранённой истории клиента с подписью «Специалист EnergyTool», не как ответ модели. Обновите клиентскую страницу, чтобы получить внешнее обновление.
- Специалист создаёт обобщённый черновик знания. **Другой** оператор с ролью редактора проверяет пять условий и одобряет публикацию. Отзыв исключает запись из поиска. Тестовые знания в рабочий поиск не входят.
- Снимок базы передаётся Python через отдельный том только для чтения. Изменения подхватываются при следующем поиске, без перезапуска модели. Исходная база организаторов не изменяется.

## Архитектура и решения

```text
Браузер: чат / карточка / заявки / специалист
  → веб-прокси :8768 → Go API :8080 → Python :8090 → OpenAI-совместимая модель
                         ↓               ↑
                 сессии и заявки     N2-поиск по базе
                         ↓               ↑
                 редактор знаний → проверенный снимок (read-only)
```

Поиск веба использует алгоритм N2: BM25 + символьные n-граммы, объединение рангов и дополнение документов ограничениями. Контекст и JSON-ответ адаптированы для интерактивного сценария, поэтому балл замороженного CSV-архива N2 **не является оценкой веба**. `WEB_RETRIEVAL_MODE=a2` на хосте Compose позволяет проверить прежний поиск. Смысловой B2 не включён по умолчанию: его платформенный результат 45,877 ниже A2 55,969; найденный дефект многострочного запроса исправлен, причинность снижения не доказана.

Подробнее: `docs/architecture-decisions.md`, `docs/business-contract.md`, `docs/expert-contract.md`, `docs/release-readiness.md`.

## Настройки и порты

| Настройка | Назначение |
|---|---|
| `LLM_BASE_URL` / `OPENAI_BASE_URL` / `BASE_URL` | Адрес API, обычно с `/v1`; первое непустое имя имеет приоритет |
| `LLM_API_KEY` / `OPENAI_API_KEY` | Выданный ключ, передаётся как `Authorization: Bearer` |
| `LLM_MODEL` / `OPENAI_MODEL` / `GEN_MODEL` | Выданный идентификатор модели, без подмены на локальную |
| `MAX_TOKENS`, `TEMPERATURE` | В примере 1536 и 0; стандартные параметры `/chat/completions` |
| `CONTEXT_CHARS`, `TOP_K` | В примере 14000 символов базы и 6 основных фрагментов с дополнением документов |
| `MAX_WORKERS`, `LLM_TIMEOUT`, `LLM_ATTEMPTS` | В примере 1 запрос, 90 секунд на попытку, до 2 транспортных попыток |
| `WEB_PORT`, `WEB_ENV_FILE` | На хосте Compose: 8768 и `.env.web` |
| `WEB_RETRIEVAL_MODE` | На хосте Compose: `n2`, альтернатива `a2` |
| `DEMO_MODE` | На хосте Compose: `true`; помечает новые сессии демоданными |
| `OPERATOR_TOKEN` | На хосте Compose: демонстрационный ключ оператора |

Открыт только `127.0.0.1:8768`; порты 8080 и 8090 доступны внутри Docker. Python использует стандартную библиотеку (`requirements.txt` без внешних пакетов); Go — стандартную библиотеку (`backend/go.mod`). Базовые образы закреплены digest. Node.js/Playwright и инструменты PDF нужны для разработки и проверки, не для запуска продукта.

## Проверки

```bash
python3 -m unittest discover -s tests -q
(cd backend && go vet ./... && go test -race ./...)
python3 tools/host_tests/test_web_stack.py
```

`tests/test_organizer_web.py` проверяет адрес, ключ, модель и структуру реального HTTP-запроса на тестовом сервере для всех имён переменных организаторов. Это **не вызов закрытого API организаторов**. `tools/benchmark_web.py --url http://127.0.0.1:8768` выполняет 10 последовательных синтетических запросов и сохраняет медиану, p95 и ошибки. Браузерные проверки лежат в `tools/host_tests/`.

Фактические результаты выпуска и ограничения: `docs/release-readiness.md` и `reports/release-validation/`. Часть тестов использует контролируемые ответы; они подтверждают инфраструктуру, не качество генерации.

Аудит взаимодействий от 15 ноября: `docs/ui-interaction-audit.md`. Новые проверки восстановления: `tools/host_tests/test_wait_recovery.cjs`, `test_navigation_recovery.cjs`, `test_specialist_recovery.cjs`, `test_wait_recovery_stack.py`.

Последующий прогон с настоящей моделью, прерыванием, возвратом и заявкой: `docs/live-user-audit.md`. Ответы, длительности, снимки экранов и результаты альтернативных сценариев: `reports/live-user-audit-20261115/`.

## Ограничения и запасной показ

- Локальная модель отвечает существенно дольше ориентира 5–7 секунд. Таблица живого замера включает ошибки; заявлять достигнутый SLA нельзя. Производительность модели организаторов здесь не измерена.
- Без доступной модели новый содержательный ответ получить нельзя. Сессии, история, сохранение заявки, очередь и специалист продолжают работать; для защиты приложена запись рабочего сценария на нашем стенде.
- Валидатор проверяет происхождение цитат и фактов клиента, но не доказывает семантическую правильность каждого утверждения. Повторные вопросы подавляются/исправляются в пределах ограниченной попытки; ошибки генерации остаются видимыми.
- Хранилище — локальный JSON и один экземпляр Go API. Для промышленного внедрения нужны БД, авторизация клиентов и сотрудников, ограничение нагрузки, мониторинг и резервирование.
- CRM и внешняя отправка не подключены. Метрики демонстрационного стенда не являются результатами пилота или доказанным ростом конверсии.

`experiments/`, старые `reports/`, `artifacts/` и `handoffs/` содержат историю исследований, не требуются для работы веба. Старый журнал сохранён в `docs/ml-readme-history.md`. Организаторские материалы, реальные сессии, действующие ключи и `.env.web` не публикуются в Git.
