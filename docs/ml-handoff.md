## Когда появится API

1. Заполнить окружение, начать с MAX_WORKERS=1 и небольшого числа запросов. Модель и URL брать из предоставленных настроек.
2. Проверить один демонстрационный вопрос через `answer_only=True`: фактический текст, найденный контекст, задержку и технический статус. Отдельно проверить полный режим бэкенда с цитатами и заявкой.
3. Выполнить `python3 tools/evaluate.py --mode live`. Для каждого сценария сопоставить ответ с рубрикой, базой и демонстрационным образцом. Не оценивать только буквальное совпадение.
4. Отдельно отмечать ошибки поиска, генерации, истории, заявки и API. Особое внимание — неподтверждённым обещаниям, отказу от телефона, исправлениям и подмене ролей.
5. Если нужного фрагмента нет — править поиск с Артёмом. Если он есть, а ответ неверен — править промпт/контракт и повторять затронутые сценарии. Не добавлять готовые ответы известных вопросов в runtime.
6. Замерить задержку, долю технических ошибок и число повторов на реальном прокси; после этого выбирать параллелизм и размер контекста. Из mock-времени производительность Qwen не выводится.

## Следующий сабмит

1. После изменений выполнить `python3 tools/check_all.py`; получить актуальный ZIP и SHA-256.
2. Новый кандидат готовится отдельно по [плану повышения результата](score-improvement-above60-tz.md); повторная загрузка v3 или A2 ради новой попытки не требуется. Перед загрузкой проверить актуальный лимит и счётчик команды. Подготовка архива сама по себе не означает его отправку.
3. После разрешённой загрузки дождаться завершения и записать время по МСК, SHA-256, общий Score, статус и длительность. По Q&A №43 и №46 Match Rate, Win Rate и ошибки по отдельным вопросам команде не раскрываются. Статус «на проверке» не считать успешной оценкой.
4. При 401 сообщить организаторам; не подменять служебный ключ. При тайм-ауте исследовать число запросов, задержку и контекст.
5. Для допуска нужен Score > 0 вместе с веб-прототипом и полным комплектом финальной сдачи.

## Совместная приёмка

С Артёмом: согласовать стабильные document_id/chunk_id, полноту оговорок, время подготовки поиска и соответствие условиям ZIP. С Игорем: передавать только текущую сессию, сохранять все сессии и заявки, сериализовать изменения истории, проверить новый диалог после сохранённой заявки. С Георгием: показывать время и использованные источники в отладке, поддержать отказ от телефона, не показывать «отправлено» при `sent=false`.

Новая приёмка по Q&A: обращение с одним телефоном не блокируется отсутствием компании/полного имени; контакт и 1–2 предложения о реальной задаче доступны в человекочитаемом виде. Чистый контактный шаг без продуктовых утверждений не должен ломаться из-за требования цитаты базы. Для демо достаточно общего самостоятельного интерфейса и сохранённой заявки; кабинеты, авторизация и CRM не нужны.

Общий Docker, веб-сценарий, презентация, ссылка на репозиторий/доступ жюри и демонстрация остаются командной работой. Материалы ML уже содержат объяснение архитектуры, ограничений и воспроизводимый порядок проверки.

Docker ML повторно проверен 10 ноября 2026 года с локальным mock API без внешних запросов к модели. Проверены UID 10001, входные данные только для чтения, корректная диагностика отсутствующих настроек и совпадение исходников образа с ZIP. Отчёты: `reports/docker-validation.json`, `reports/python-compatibility.json`. Полный прогон: `python3 tools/check_all.py --docker --python-compat python:3.9-slim`. Подробности исправлений: `docs/api-compatibility-audit.md`.

## Что нельзя утверждать на защите

Нельзя говорить «модель прошла 30 сценариев», «получен высокий Score», «галлюцинаций нет», «измерена скорость Qwen» или «заявка отправляется менеджеру». Сейчас подтверждены только перечисленные программные проверки и локальный протокол. После реального прогона эти утверждения можно уточнить по сохранённым результатам.
