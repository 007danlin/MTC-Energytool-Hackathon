# Архитектурные решения: что выбрали и почему

Для каждого решения указаны альтернатива, причина с опорой на измерения или правила кейса и ограничение. Всё, что не проверено, помечено явно.

## Решения

| # | Решение | Альтернатива | Почему | Ограничение |
|---|---|---|---|---|
| 1 | База режется **по заголовкам** на 234 фрагмента (медиана около 420 символов) | окна фиксированной длины | Число остаётся в одном разделе со своей оговоркой и со списком «чего утверждать нельзя». Критично: выдумка и неподходящее решение названы организаторами самыми опасными ошибками (Q&A №4) | Разделы без заголовков не делятся |
| 2 | Поиск в конкурсном N2: **BM25 + символьные n-граммы, объединение RRF** | эмбеддинги, реранкер | Находит словоформы («опт» → «оптовый»), быстрый, предсказуемый, без внешних сервисов. Эмбеддинги проверили отдельно: bge-m3 поднял долю вопросов, где в контексте есть все нужные факты, с 92% до 99% (93 вопроса, локально). Но версия B2 с этим поиском на платформе набрала **45,9 против 56,0 у A2**; причину однозначно не установили (`docs/b2-platform-postmortem-20261112.txt`). Один дефект нашёлся в нашем коде: для сообщения из нескольких строк смысловой поиск видел только первую строку. Он исправлен (`tests/test_hybrid_query.py`), на платформе повторно не проверялся | Реранкер на обычном процессоре не измерили. Рост поиска на наших вопросах ≠ рост балла на платформе |
| 3 | В контекст идут **документы продукта целиком** и правила продукта | только лучшие фрагменты | Цифры не отрываются от условий; релевантные правила «не подходит, если» дополняют контекст | Контекст длиннее; веб ограничивает общий бюджет и число документов, поэтому не каждый документ входит целиком |
| 4 | **Один шаг RAG**, не агентный | модель сама выбирает документы, повторные поиски | Нужен ответ за 5–7 секунд (Q&A №27). Двухшаговый вариант с выбором фрагментов моделью проверили: прироста не дал, времени ушло вдвое больше | Нет самопроверки ответа |
| 5 | **Консультант на Python отдельно, API и сессии на Go** | один сервис | Консультант не хранит состояние; Go держит историю, блокировки, лимиты. Можно менять поиск и модель без правок API | Два процесса и HTTP между ними |
| 6 | **Источники проверяет сервер**: модель называет ID фрагментов, сервер подставляет точный текст | модель сама пишет цитаты | Цитату нельзя придумать | Подтверждает происхождение источника, а не каждое утверждение |
| 7 | Сессии в **JSON-файле** с атомарной записью | PostgreSQL | Для демо достаточно, ничего не нужно ставить. Интерфейс хранилища позволяет заменить файл на базу данных | Один процесс, для рабочей системы не годится |
| 8 | Заявка формируется **внутри решения**, CRM не подключаем | интеграция с CRM | Q&A №17 и №21 не требуют интеграции. Контракт будущей передачи описан: `docs/business-analysis.md`, раздел 6 | Менеджер получает файл или запись в очереди, не сделку в CRM |
| 9 | **Карточка потребности** собирается из подтверждённых данных без новой модели | второй вызов модели для резюме | Не выдумывает: у каждого значения статус и ссылка на сообщение клиента; цитата принимается, только если дословно есть в реплике клиента | Качество зависит от резюме консультанта |
| 10 | Новые знания попадают в базу **только через человека** | модель пополняет базу сама | Новые факты, цены и ограничения нельзя подтверждать уверенностью модели. Ответ клиенту и запись в базу — разные объекты, личные данные в базу не попадают | Нужен ответственный проверяющий |
| 11 | Для веба — **заменяемый OpenAI-совместимый API** | платформенная Qwen3.8-27B | Веб проверен на локальной модели; выданные адрес, ключ и идентификатор можно подключить через окружение без изменения кода | Скорость и качество веба не равны платформенным |

## Как встроить в сайт Energytool

Сейчас кнопка «Онлайн-консультация» открывает страницу чата на том же домене. Запросы к `/api/v1/*` сайт передаёт Go API (тот же домен). Поэтому не нужны CORS и ключи в браузере.

Для рабочего сайта:
1. Оставить схему «сайт передаёт `/api/v1` сервису консультанта».
2. Подключить как кнопку-виджет: ссылка или `iframe`, открывающий страницу чата.
3. Перед выходом в интернет добавить вход, ограничение числа запросов и хранение в базе данных.
4. Журналы вести без телефонов, имён и текстов реплик.

## Как передавать заявки менеджерам

- **Сейчас:** заявка сохраняется, скачивается в TXT/JSON; карточка потребности и очередь статусов описаны в `docs/business-contract.md`.
- **Дальше:** передача из работающей очереди в CRM по контракту: ключ `application_id:vN` (повтор не создаёт вторую сделку), статусы `confirmed` / `delivered` / `error`. `delivered` ставится только по ответу CRM.

## Идеи развития

- N2-поиск подключён через `web_retrieval.py`; отдельно измерить качество адаптированного веб-ответа на модели организаторов.
- Заново проверить поиск по смыслу на платформе после исправления дефекта: версия B2 набрала меньше A2.
- Пилот на одном-двух направлениях сравнить с обычной формой заявки (см. `docs/business-analysis.md`).
- Цикл «бот не знает → специалист отвечает → проверенная запись в базе» подключён. Следующий этап — промышленная авторизация и независимая редакторская проверка.
