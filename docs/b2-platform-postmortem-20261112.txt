Ошибка решения о выпуске
Локальные проверки давали основание для гипотезы об улучшении, но не для
уверенной рекомендации следующего ZIP. Основные 93 вопроса уже применялись
при разработке; оценивал один Codex. Локальная Qwen3-VL-30B-A3B Q4_K_M
отличается от платформенной Qwen3.8-27B. Официальный Score равен
0.7 × MatchRate + 0.3 × WinRate относительно скрытых эталонов/baseline,
поэтому 23 локальные победы над A2 и 7 поражений не прогнозируют Score.
Качество сравнивали с предвычисленными контекстами: живой embedding API
платформы не был проверен. Равенство 93 запросов B/B2 восстановлено офлайн.
Два новых существенных провала B (e054, e089) оставались. На восьми новых
солнечных вопросах B2 выиграл 2, проиграл 1, получил 5 ничьих; обе версии
существенно ошиблись в 3 из 8. Ничья не обязательно означает верный ответ.

Что установлено аудитом точных архивов
1. Генератор, prompts, LLM client, consultant, dialogue, lexical retrieval
   и requirements в A2 и B2 побайтно одинаковы. Отличаются solution.py,
   settings.py; в B2 добавлен hybrid_retrieval.py.
2. B2 повышает запрошенный TOP_K=4 до 12, включая RETRIEVAL_MODE=a2
   и fallback. В исходном A2 остаётся 4. В примере организатора default=4,
   но фактическое значение платформы неизвестно. Поэтому для возврата
   нужен исходный A2 ZIP: переключатель в B2 не гарантирует тот же режим.
3. В B2 _split_query берёт первую непустую строку текущего сообщения для
   dense-поиска. Воспроизведено: из «Здравствуйте!\nНужна солнечная станция
   510 кВт.\nЕсть ли ограничения по мощности?» dense получает только
   «Здравствуйте!». Лексическая часть и генератор видят полный вопрос.
   Это настоящий дефект, но его вклад в скрытый балл не установлен.
4. Новый сетевой путь индексирует базу пакетами по 16 (общий startup limit
   90 секунд); query embedding ограничен 8 секундами без повторов, после
   трёх последовательных сбоев dense выключается. Сбой API на платформе
   не доказан. Endpoint/имена ключей/модель соответствуют примеру; реранкер
   по умолчанию выключен. Недостающих runtime-зависимостей не найдено.
5. «Успешно» означает принятый запуск, но не исключает технических ответов
   внутри валидного CSV. Время 337.9 с не доказывает общий timeout при
   лимите 20 минут; время напрямую не входит в формулу Score.

Чего мы пока не знаем
Нет ответов, stdout, эффективных параметров и per-question результатов
платформы. Нельзя выбрать между влиянием контекста, ошибками retrieval API,
многострочными вопросами, другой моделью или распределением скрытого теста.
Ни одной из этих гипотез не присвоен статус причины падения.

Дальнейшее решение
Сохранить A2 как лучший подтверждённый вариант; не повторять отправку B2.
Если платформа требует выбрать финальную посылку, выбрать уже оценённый A2.
Следующий кандидат допустим после проверки конкретной причины: один фактор
за эксперимент, отдельный контроль новых существенных ошибок, абсолютного
выполнения требований и независимый набор по всем продуктам. Если доступны
логи платформы, сначала проверить inputs_ready, retrieval, statuses,
фактические параметры и количество технических ответов. Без логов не
подменять неизвестную причину уверенным объяснением.
В этом разборе новые генерации, исправления runtime, архивы и отправки
не выполнялись. Существующие ZIP и замороженные оценки не изменены.
