# Презентация: содержание по слайдам

Для Георгия (оформление) и для всех, кто выступает. Ориентир организаторов: около 7 минут на рассказ и время на вопросы жюри (Q&A №48). Формат сдачи: PDF с ссылкой на репозиторий **на первом слайде** либо ZIP с кодом и PDF.

## Слайд 1. Титул и как проверить (обязательно)

- Название: «МТС Energytool: ИИ-консультант для сайта», команда, роли в одну строку.
- Ссылка на репозиторий: `github.com/007danlin/MTC-Energytool-Hackathon` (приватный; доступ открыт аккаунту жюри `hack-and-change-2026` — проверить перед отправкой).
- **Порядок проверки (3 строки):** 1) положить `data/knowledge-base.zip`; 2) `cp .env.web.example .env.web` и вписать адрес модели; 3) `docker compose -f compose.web.yaml up --build -d`, открыть `http://127.0.0.1:8768`.
- Ссылка на развёрнутый интерфейс — если будет; если нет, не писать.
- Код сдачи: файлы из раздела «Как проверить основной сценарий» в `README.md`.

## Слайд 2. Проблема и пользователь (≈50 с)

- Около 400 тысяч компаний могут быть клиентами: ретейл, склады, торговые центры, СНТ, сетевые компании.
- Клиент не разбирается в тарифах, ценовых категориях, порогах мощности. Выбрать решение сложно.
- Сейчас: форма на сайте, менеджер заново выясняет задачу на звонке.
- Цель МТС: **больше качественных заявок.**

## Слайд 3. Сценарий консультации (≈60 с)

Схема пути: вопрос своими словами → уточняющие вопросы → подбор продукта из базы → ответ простым языком → «в базе этого нет» + специалист → заявка с резюме.
Правила: факты только из базы, не выдумываем цены, не предлагаем неподходящее до понимания ситуации, отказ мягкий.

## Слайд 4. Архитектура (≈60 с)

Схема из `README.md`: сайт → Go API → консультант на Python → модель. Две строки про каждый блок.
Тип RAG: гибридный поиск по словам и частям слов, документы продукта целиком с правилами, проверка источников. Почему не агентный и не на эмбеддингах: `docs/architecture-decisions.md`.

## Слайд 5. Как проверяли качество (≈60 с)

- Платформа: баллы 5,8 → 50,4 → 56,0 → 58,8 → **69,9** (N2). Это балл платформы, не процент точности.
- Свой проверочный набор: 123 вопроса, 154 обязательных факта, запреты.
- Честно: N3 дала 62,0; разброс по одиночным прогонам объяснить нельзя. Поиск по смыслу улучшил наш локальный замер, но версия с ним (B2) на платформе набрала 45,9 против 56,0 у A2. Мы нашли и исправили дефект в нашем коде, причину падения однозначно не установили.

## Слайд 6. Примеры работы (≈70 с)

Три коротких диалога со скриншотами (только тестовые данные):
1. Вопрос и уточнение (например, склад с дневной работой и высокими счетами).
2. «В базе этого нет» и предложение специалиста.
3. Клиент не из целевого сегмента: мягкий отказ и альтернатива.
К каждому: что видно в режиме отладки (время и документы).

## Слайд 7. Ценность для бизнеса и пилот (≈60 с)

- Карточка потребности вместо повторной анкеты: что известно (со ссылкой на слова клиента), что нет, следующий шаг.
- Очередь и статусы заявки, пять метрик пилота (конверсия в заявку, доля принятых, время до заявки, время разбора, потери пути).
- Пилот: 4 недели на 1–2 направлениях, сравнение с обычной формой. **Цели — гипотезы:** организаторы фиксированных не задали (Q&A №41). Цифры стенда не выдавать за реальные.

## Слайд 8. Ограничения и идеи (≈50 с)

Ограничения: скорость веба на локальной модели, N2 пока не в вебе, нет авторизации и CRM, хранилище-файл.
Идеи: подключить N2 к вебу, поиск по смыслу, цикл «специалист → проверенная запись в базе», передача в CRM по контракту.
