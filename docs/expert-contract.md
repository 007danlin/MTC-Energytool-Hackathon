# Обращение к специалисту и проверенные знания: контракт (v0.2, черновик)

Автор: Артём. Пакет: `backend/internal/expert/` (ветка `artem/expert`). Основа — `main` `62be5cb`.
Путь: **неизвестный вопрос → обращение → ответ специалиста клиенту → проверенная запись знаний → повторное использование.**
Имена путей и структуру хранения Игорь может уточнить; смысл состояний фиксирован.

## 1. Обращение (`Request`)

### Когда создаётся

Только по структурированному результату консультанта `status = knowledge_gap`, привязанному к сохранённому сообщению клиента.
`answered`, `clarification`, `out_of_scope`, `technical_error` обращение **не** создают. Текст ответа модели («не знаю» и т.п.) не анализируется.

Вход (`GapSignal`) Игорь заполняет после сохранения ответа консультанта:

```json
{
  "session_id": "s-1",
  "origin_message_id": "m-7",
  "result_status": "knowledge_gap",
  "demo": true,
  "at": "2026-11-13T10:00:00Z"
}
```

Плюс `messages` сессии (`id`, `role`, `content`, `sequence`). Вопрос — точный текст исходного сообщения клиента.
Контекст — до 3 предыдущих **реплик клиента** со ссылками на сообщения; ответы бота и весь диалог не пересылаются.
Телефон и заявка не нужны; `application_id` — необязательная ссылка.

**Ключ уникальности:** `session_id + origin_message_id`. Повтор сигнала возвращает прежнее обращение без изменений.
Похожие вопросы разных клиентов — разные обращения: диалоги и контакты не смешиваются.

### Состояния

```text
queued ──take (назначенный)──> in_review ──answer (назначенный)──> answered
  │                               │
  └──cancel (координатор/назначенный, причина)──> cancelled <──┘
assign / reassign (координатор): в queued и in_review; переназначение из in_review возвращает в queued
```

| Действие | Кто | Из | В |
|---|---|---|---|
| `assign` | `coordinator` | queued, in_review | queued |
| `take` | назначенный `specialist` | queued | in_review |
| `answer` | назначенный `specialist` | in_review | answered |
| `cancel` (+ причина) | `coordinator` или назначенный | queued, in_review | cancelled |

`answered` — ответ сохранён; это не доставка и не прочтение. Причины отмены: `duplicate`, `not_relevant`,
`resolved_elsewhere`, `other`.

### Статус для клиента

| Условие | `client_status` | Текст |
|---|---|---|
| queued, не назначено | `awaiting_assignment` | Вопрос зарегистрирован, ожидает назначения специалиста |
| queued, назначено | `assigned` | Вопрос передан специалисту |
| in_review | `in_review` | Специалист готовит ответ |
| answered, доставка не завершена | `answer_pending` | Ответ специалиста готовится к выдаче |
| answered, delivered | `answered` | Ответ специалиста |
| cancelled | `cancelled` | Обращение закрыто |

«Передано специалисту» показывается только после сохранённого назначения. Факт прочтения не показывается.

## 2. Ответ специалиста (`Reply`) и доставка

- Один окончательный ответ на обращение. Автор — назначенный специалист. Текст хранится точно и показывается клиенту
  с пометкой **«Ответ специалиста»**; модель его не переписывает. Ответ не ждёт одобрения общей базы.
- Сохранение ответа в той же записи создаёт намерение доставки `delivery = pending`.

| Доставка | Значение |
|---|---|
| `pending` | ответ сохранён, ещё не добавлен в данные сессии |
| `delivered` | ответ доступен в сохранённой истории исходной сессии (не прочтение) |
| `failed` | добавить не удалось; `retry_delivery` → снова `pending`, **тот же** ответ |

Для закрытой сессии ответ добавляется в её историю как связанный элемент; сессия заново не открывается.

## 3. Команды, повторы, версии

Каждая команда: `expected_version`, `command_id`, данные. Автор и роль — **только из доверенного серверного контекста**
(не из тела запроса клиента).

- Тот же `command_id` с тем же содержимым — возвращает текущую запись, второго ответа/события нет.
- Тот же `command_id` с другим содержимым — `request_conflict`.
- Устаревшая `expected_version` — `version_conflict`.

**Граница атомарности (Игорь):** обращение, ответ, намерение доставки, `command_id` и журнал действий сохраняются
одной записью под блокировкой обращения. Создание по сигналу — под блокировкой ключа `session_id + origin_message_id`.
Добавление ответа в сессию — под блокировкой сессии, идемпотентно по `reply_id`.

## 4. Проверенные знания (`KnowledgeEntry`)

Отдельный объект, не копия ответа клиенту. Поля ревизии: `title`, `generalized_question`, `answer`, `applicability`
(область применимости), `basis` (основание), `author_id`, `reviewer_id`, `reviewed_at`, чек-лист проверки.
Связь с исходным обращением хранится внутри и в публичный источник не попадает.

### Редакционные состояния ревизии

```text
draft ──approve (проверяющий, чек-лист)──> approved ──revoke (причина)──> revoked
правка approved → новая draft-ревизия; прежняя approved действует до активации замены или отзыва
```

Перед созданием черновика: обязательные поля; нет телефонов, e-mail, идентификаторов сессии/обращения;
обобщённый вопрос не совпадает дословно с вопросом клиента.
Одобрение требует отметки всех пунктов чек-листа: факт подтверждён, условия указаны, нет противоречия
материалам, нет частных данных, текст пригоден для повторного использования.
Один человек в прототипе может быть автором и проверяющим, но действие и роль фиксируются отдельно.

### Состояние в поиске (`runtime_status`) — отдельно от одобрения

| `runtime_status` | Значение |
|---|---|
| `pending` | одобрено/отозвано, поиск ещё не обновлён |
| `active` | входит в активную версию базы `kb_version` |
| `failed` | активация не удалась — запись остаётся одобренной, ошибка видна |
| `inactive` | заменена новой активной ревизией или отозвана и исключена |

`approved` ≠ «доступно боту». «Доступно боту» — только `active` с фактической `kb_version` от Игоря.

### Выгрузка для поиска (Игорю)

`ActiveSet` — для каждой записи ровно одна ревизия: последняя `approved` неотозванная. Черновики не входят.
`RenderForKB` — Markdown-документ без автора, проверяющего, ID обращения и сессии:

```text
path: 90-expert/<entry_id>-r<revision>.md   → source_id: 90-expert/<entry_id>-r<revision>.md#s001
```

Игорь собирает активную версию базы (исходная база + документы `ActiveSet`), получает `kb_version` и вызывает
`ApplyActivation(kb_version, включённые ревизии | ошибка)`.

## 5. Ошибки

| Ошибка | HTTP | `code` |
|---|---|---|
| `ErrVersionConflict` | 409 | `version_conflict` |
| `ErrRequestConflict` | 409 | `request_conflict` |
| `ErrInvalidTransition` | 409 | `invalid_transition` |
| `ErrForbidden` | 403 | `forbidden` — роль/автор не допускаются к действию |
| `ErrInvalidInput` | 422 | `invalid_input` |
| `ErrPrivateData` | 422 | `private_data` — в тексте знания найдены контакты/идентификаторы |
| `ErrChecklistIncomplete` | 422 | `checklist_incomplete` |
| не `knowledge_gap` | — | обращение не создаётся, это не ошибка |

## 6. Функции пакета и интерфейсы хранения (для Игоря)

| Шаг | Функция `expert` |
|---|---|
| после ответа консультанта | `RegisterGap(existing, GapSignal, messages, newID, now)` — под блокировкой ключа `RequestKey(session_id, origin_message_id)` |
| очередь специалиста | `RequestStore.List(RequestFilter{Status, AssigneeID})` |
| действия | `Assign`, `Take`, `Answer`, `Cancel` — `(request, actor, Command{expected_version, command_id}, …)` |
| доставка | `MarkDelivered`, `MarkDeliveryFailed`, `RetryDelivery` — актор `system` |
| статус в чате клиента | `StatusForClient(request)` |
| ответы API | `PublicRequest`, `PublicEntry` — без служебного журнала команд |
| знания | `NewDraft`, `EditDraft`, `Approve`, `Revoke` |
| сборка базы | `ActiveSet(entries, test)` → документы → `kb_version` → `ApplyActivation(entry, system, cmd, ActivationResult)` |
| «доступно боту» | `AvailableToBot(entry)` — только `active` с `kb_version` |

`RequestStore` / `KnowledgeStore` — интерфейсы в `repo.go`: `Save(record, previousVersion)` — сравнение с сохранённой версией
(0 — создание), иначе `ErrVersionConflict`; ключ `session_id + origin_message_id` уникален. Эталонная реализация в памяти
`MemoryStore` и `RegisterGapAtomically` показывают нужные гарантии; тест: 20 параллельных сигналов дают одно обращение,
сохранение по устаревшей версии не затирает чужое действие. Тестовые записи знаний (`test: true`) попадают только
в отдельную тестовую базу демо (`ActiveSet(entries, true)`).

## 8. Сценарий демонстрации (после интеграции)

1. Клиент задаёт вопрос вне базы → `knowledge_gap` → обращение «ожидает назначения».
2. Координатор назначает специалиста → клиент видит «передано специалисту»; специалист видит обращение в очереди.
3. Специалист берёт в работу и отвечает → клиент получает **точный** текст с пометкой «Ответ специалиста».
4. Повтор команды ответа и перезапуск не дублируют ответ.
5. Автор готовит обобщённую запись, проверяющий одобряет → `approved`, `runtime: pending` → активация → `active, kb_version`.
6. Новый клиент задаёт переформулированный вопрос в области применимости → ответ с источником `90-expert/<id>-r1.md`.
7. Вопрос за пределами области применимости не получает ложной рекомендации; черновик не находится; после отзыва запись не используется.

Логика (тесты пакета), API и живой сценарий отмечаются отдельно. Mock-тесты не означают завершённую интеграцию.
