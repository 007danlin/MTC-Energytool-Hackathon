# Совместный запуск сайта, Go и Python

Схема: браузер → сервер сайта `/api/v1/*` → Go API → Python `/respond` → локальная Ollama `/v1/chat/completions`.

Внешнего тестового API платформенной Qwen в документации нет. На рабочем Mac уже установлена `energytool-qwen-local-eval:20261110`: Qwen3-VL-30B-A3B Instruct Q4_K_M, контекст 16384, seed 42, temperature 0. Работает Ollama на `127.0.0.1:11434`. Это локальная модель, отличающаяся от платформенной; см. `local-qwen-evaluation.md`. Новые веса для веб-запуска не нужны. Строка `local-ollama` в настройке ключа — заполнитель для существующего клиента; локальная Ollama не требует внешнего ключа.

## Что нужно коллегам после git pull

В Git включены сайт со статическими ресурсами и шрифтом, Go-бэкенд, Python-адаптер, Dockerfile/Compose и тесты. Конкурсный N2 сохранён отдельно; веб использует корневой консультант на базе A2. Перенос N2 — отдельная задача Игоря.

Базу `data/knowledge-base.zip` возьмите из выданного команде пакета организаторов. Для веба `questions.csv` не нужен. Веса модели, исходная база, реальные `.env` и история клиентских сессий в Git не входят. Указанный в `.env.web.example` псевдоним модели существует на рабочем Mac Даниэля; на другом компьютере задайте свой доступный совместимый endpoint и модель. Одного `git pull` без этих внешних зависимостей недостаточно для генерации.

Для тестов без настоящей модели достаточно Python 3.9+ и Go 1.22+; см. команды ниже. Docker-образы используют Python 3.11. Для браузерных тестов дополнительно нужны Node.js, пакет `playwright` и Chromium (`npx playwright install chromium`).

## Запуск на этом Mac

Нужны Docker Desktop, запущенная Ollama, установленная модель и `data/knowledge-base.zip`.

```sh
# Из корня репозитория; не перезаписывайте уже настроенный файл.
cp -n .env.web.example .env.web
ollama list
docker compose -f compose.web.yaml up --build -d
```

Откройте **http://127.0.0.1:8768**, нажмите «Онлайн-консультация». Старый отдельный предпросмотр может продолжать работать на 8767. Порт полного приложения меняется через `WEB_PORT`. Отдельный файл окружения можно выбрать через `WEB_ENV_FILE`.

Внутри Docker `host.docker.internal:11434` указывает на Ollama хоста. Для другого компьютера укажите установленную модель и доступный URL в `.env.web`. При запуске без Docker используйте `http://127.0.0.1:11434/v1`. Сервис не скачивает модели и не переключается автоматически на внешнего провайдера.

```sh
curl -f http://127.0.0.1:8768/health/ready
docker compose -f compose.web.yaml logs --tail=20
docker compose -f compose.web.yaml down
```

`down` сохраняет историю в volume `energytool-web_sessions`; `down -v` удаляет её. Go и Python не публикуют порты на хост. Сайт доступен только через loopback. Авторизации пока нет: все диалоги доступны пользователям локальной демонстрации, а не разграничены по аккаунтам. Не публикуйте эту конфигурацию как многопользовательский сервис.

## Поведение

- При первом открытии создаётся сессия; её ID сохраняется в браузере. Сама история и заявки хранятся в Go, в JSON-файле volume.
- Можно создавать и переключать диалоги. Новая сессия получает пустой контекст. Завершённые диалоги доступны для чтения.
- Сообщения и ответы выводятся как текст. Источники и время выбранного ответа доступны в режиме отладки; заявка открывается через меню или после ответа.
- Подтверждённые в новом интерфейсе заявки сохраняются в `session.application` и скачиваются как TXT. Отправки менеджеру или в CRM нет. Формы исходного сайта и авторизация МТС остаются демонстрационными.
- После сетевого сбоя нужно обновить историю кнопкой ↻ перед повторной отправкой. Автоматических повторов POST нет.
- Веб-адаптер предлагает модели выбирать фрагменты по `evidence_id` и подставляет их точный текст в цитаты. Неизвестные ID и несоответствие `source_id` отклоняются. Это проверка происхождения источника, а не доказательство каждого утверждения ответа. Python проверяет входной контракт, ограничения истории и принадлежность заявки сессии; использует существующий `respond_json`, поиск и валидацию цитат. При неверной цитате ответ может стать `technical_error`: интеграция не отключает проверку источников ради показа ответа.
- Максимум 200 сообщений / 100000 символов истории, 10000 символов одного сообщения; HTTP-тело сообщения ограничено 32 КиБ. При лимите нужно начать новый диалог.

## HTTP-адаптер

`consultation_http.py` загружает настройки и базу один раз. `POST /respond` принимает контракт из `ml-integration.md`. `GET /health/live` и `/health/ready` возвращают 200 после успешной инициализации. Readiness проверяет доступность процесса с загруженной базой, но не вызывает модель и не гарантирует её доступность.

Невалидный вход — 400, слишком большое тело — 413, неверный Content-Type — 415, занятые слоты модели — 503. Ошибки не содержат текста запросов, ключей и внутренних ответов. По умолчанию внутренний лимит тела — 1 МиБ, бюджет обращения — 240 секунд; для локальной Qwen один рабочий слот, одна транспортная попытка. Клиент Go ждёт 250 секунд, запрос Go ограничен 255 секундами, прокси — 260, браузер — 275. Холодная загрузка модели входит в бюджет.

Для запуска без Docker экспортируйте настройки из `.env.web`, заменив URL Ollama на loopback, затем в трёх терминалах из корня:

```sh
python3 consultation_http.py
(cd backend && BACKEND_ADDR=127.0.0.1:8080 ML_SERVICE_URL=http://127.0.0.1:8090 go run ./cmd/api)
WEB_PORT=8768 python3 local-preview/energytool-site/serve.py
```

## Проверки

```sh
python3 -m unittest discover -s tests -q
python3 -m unittest tools.host_tests.test_web_stack -v
(cd backend && go test -race ./... && go vet ./...)
node --check local-preview/energytool-site/www/chat.js
```

Сквозной автоматический тест запускает реальный Go, Python HTTP и прокси сайта с тестовым OpenAI HTTP-сервером. Он проверяет сериализацию, цитаты, две изолированные сессии, историю после перезапуска Go, закрытие и отказ Python. Это проверка интеграции, а не качества ответов модели. CSV-сабмит по-прежнему запускается исходным `compose.yaml`; веб-код не включается в сабмит-сборщик.

Полноэкранный интерфейс, исходник Figma, API заявки и браузерные проверки описаны в [consultation-ui.md](consultation-ui.md).

## Очередь заявок

На локальном стенде откройте [рабочее место менеджера](http://127.0.0.1:8768/applications.html). Экран запрашивает очередь, карточки, причины переходов, экспорт и метрики по [контракту v1.2](business-contract.md). Переписка по ссылкам из карточки читается через существующий API сессий. Статус «Принята в работу» означает решение менеджера.

Для живой приёмки нужен бэкенд, подключающий маршруты `/api/v1/applications` и `/api/v1/metrics/pilot` к хранилищу. На бэкенде без этих маршрутов экран покажет, что очередь недоступна. Проверка интерфейса использует изолированный тестовый API, настоящий прокси и Chromium. Модель и база знаний для неё не нужны.

```sh
PLAYWRIGHT_MODULE=/path/to/playwright node tools/host_tests/test_application_queue.cjs
```

Тест проверяет фильтрацию, причины и переходы, правку, повтор после сбоя, конфликт версии, файлы TXT и JSON, метрики и возврат к карточке после перезагрузки страницы. Для скриншотов задайте `WEB_TEST_SHOTS`.

## Удобное время обратной связи

В форме и редактировании заявки можно выбрать «Как можно скорее» либо дату и время по Москве (UTC+3).
Это пожелание клиента, не подтверждённая запись и не мгновенное соединение с сотрудником.
API `/api/v1/sessions/{id}/application` принимает `callback_mode` (`asap` / `scheduled`) и `callback_at`.
Для `scheduled` нужен RFC3339, например `2030-11-14T14:30:00+03:00`; сервер приводит время к МСК.
Новое время должно быть в будущем. Уже сохранённое прошедшее пожелание допускается без изменений при правке других полей.
Для `asap` время пустое; отсутствие обоих полей совместимо со старыми клиентами и означает «не указано».
Поля сохраняются в заявке; номер заявки не меняется. Бизнес-карточка передаёт пожелание в `contact_time`, TXT и JSON.
Браузерная проверка: `PLAYWRIGHT_MODULE=/path/to/playwright node tools/host_tests/test_callback_preference.cjs`.
Она использует изолированный API-имитатор и проверяет форму, сохранение, повторное открытие и переключение режима.
